# CLAUDE.md: daydream

A small atmospheric multiplayer web game running on a single dev box. Players enter a procedurally generated world that all players share and persistently mutate. See `SPEC.md` for the current acceptance contract, [`docs/PIVOT.md`](docs/PIVOT.md) for the approved 2026-09-26 pivot (platform to story: The Village of Lost Hours; the design record behind the current spec, read it before starting pivot work), `BACKLOG.md` for the deferred-ideas register, `docs/ROADMAP.md` for the post-1.0 direction, `CHANGELOG.md` for the condensed release history, `README.md` for orientation, and [`docs/gpu-and-models.md`](docs/gpu-and-models.md) for the full GPU/ML decision narrative (model picks, what we tried and rejected, what to try later).

## This repo and this instance

The GitHub repo is public, and a stranger should be able to fork it: the engine, The Village of Lost Hours, the ops templates (`ops/`), the edge Worker (`edge/`), the runbooks. It also serves exactly one live instance, the operator's village at www.eidolon.com/daydream, developed, tested and deployed from this checkout. Everything that makes that instance *this* instance stays off GitHub:

| Local only | What it holds |
|---|---|
| `instance/NOTES.md` (gitignored) | What exists only in this Cloudflare account and on this box: names, ids, rules, what is still pending, a short history. **Read it first in any prod session.** |
| `~/.config/daydream/cloudflare.env` | The Cloudflare API token and account id (0600) |
| `/etc/cloudflared/daydream.env` | The tunnel token (root only) |
| `/srv/daydream/etc/prod.env` | Prod's environment (root:daydream 0640; edit with sudo) |
| `.claude/settings.local.json` | The operator's standing grant: `bin/game prod *` and `bin/game edge *` run without a prompt (the verbs that mint a credential or a privilege or replace the world, including `prod account cli-cookie` and `prod world load`, still prompt: "Agent policy for prod") |
| Worker secrets, the dashboard | The Access service token lives only on the Worker; the Access app, tunnel route, cache and rate-limit rules live only in the dashboard (recorded in `instance/NOTES.md`) |
| `/srv/daydream/data`, `~/data/daydream` | Prod and dev data |

The committed instance values are deliberate and not secret: `edge/wrangler.toml` (routes, origin hostname, KV id, `OPERATOR`) and `ops/prod.env.example`. A fork changes those and follows [`docs/CLOUDFLARE-SETUP.md`](docs/CLOUDFLARE-SETUP.md).

**Maintenance happens in a session like the one that built it.** The operator opens Claude Code here and asks; the agent reads `instance/NOTES.md`, runs `bin/game prod status` (and `bin/game prod check` for anything public), follows the playbook in [`docs/runbooks/`](docs/runbooks/) that fits (sleep and wake, maintenance windows, deploy and rollback, content, friends, backups, incidents, the edge), and drives the prod verbs itself (see "Agent policy for prod"). When prod state changes (a dashboard rule, a token, a pending item done, a first friend), update `instance/NOTES.md` in the same session, and when a playbook was wrong, fix the playbook.

**Before any push, check the separation.** Read the outgoing diff for anything that belongs to the instance rather than the repo: tokens, keys or Cloudflare account ids; the Cloudflare account's name; the box's addresses; friends' names or invite slugs; the operator's name anywhere a player reads (players see "the Night Warden"); and confirm `instance/` is still ignored. `/security` covers secrets; this check covers the rest. Say in the push summary that it was done.

## Generation policy: local at runtime, Opus at design time

Foundational and load-bearing; it informs every design and build decision in this project. Daydream has two LLM tiers and they never blur. (The narrative version is README "Two dreamers".)

- **Runtime (the live game) uses ONLY local models on the RTX 4000.** Every generation the running game performs runs locally behind the GPU arbiter: player portraits and grown-room art (ComfyUI/SDXL; the village's own rooms and residents are rendered at design time by `bin/game prebake`), and command parsing, off-script dialogue, grown-room composition, drift variation, director ranking, and journals (vLLM/Qwen). The runtime makes NO calls to any cloud LLM. There is NO production `ANTHROPIC_API_KEY` / `OPENAI_API_KEY`, and we do not add one. A runtime feature that seems to need a cloud model is a signal to pre-bake or rethink, not to add a key.
- **Design-time heavy generation is done by Opus inside a Claude Code session**: the agent reading this file authors content and writes it into the DB / a seed, rather than the game shelling out to an API. World authoring, seeding, dreams, and grading are the main authoring path, done *at design time, with a human in the loop*, because they run in Claude Code and never in the product.
- **No API key anywhere (including dev tooling and tests) and the agent IS the design-time critic.** There is no `ANTHROPIC_API_KEY` / `OPENAI_API_KEY` in the runtime OR the tooling, and we don't add one. "Opus at design time" means THIS Claude Code agent doing the work in-session: authoring content, reasoning over the world, and reviewing generated artifacts by Reading them directly. The agent has vision, so it grades rendered images against `WHIMSY.md` itself: that IS the aesthetic gate, no cloud call. If a feature or a test looks like it wants a cloud vision/LLM call (an image-quality gate, an LLM-critic pass), that is the signal to make it an in-session agent task, NOT to add a key; a `litellm`/cloud call in tooling is the same anti-pattern as one in the runtime. (This is why the env-gated Claude-vision gate was removed 2026-07-01: it needed a key; the agent does the looking instead.) When a genuine HUMAN eye is wanted, escalate two cheap ways rather than reaching for a key: `qpeek` (`~/src/qpeek/`, driven by `bin/game test human`) shows rendered images to the operator for a rating, or just ask the operator to look in-game in the browser.
- **Pre-bake, don't phone home.** The quality ceiling of the running game is (Opus-authored story, renewed by dreams) + (local reflexes for what nobody wrote). To get Opus-grade quality in-game, bake it into the world's data ahead of time (a topic, a fact, a pool, a painting) and let the local models handle only the unanticipated.
- **Reflexes, not voice (the working stance, docs/REFLEXES.md).** The local GPU is the game's reflexes, not its voice. Every line that carries story is authored by Opus, at design time or in a dream; the 9B parses, selects among authored options, and answers only what nobody wrote; SDXL paints only what players create. When a runtime surface starts writing story, move it into authored data rather than tuning the model. Every local-model narration is tagged `src: "local"` and the dream digest lists them as candidates for authored rewrites.
- **Flag local limits at design time (process rule).** When a target experience likely won't be compelling under the local-model budget, say so explicitly during design/dev (here, in the session) and reason through the fix together (pre-bake with Opus / cache harder / simplify / accept the edge) before building. Never quietly ship a flat experience because the small model couldn't reach.

**World authoring is keyless (`world load`).** `bin/game world load <envelope.json>` (`daydream/llm/bootstrap.py:load_world`) builds a world DB from an Opus-authored JSON envelope with no LLM call and no API key: author the world in a Claude Code session, write the envelope (the schema lives in `bootstrap.py`'s system prompt), then load it. This is the canonical path. The older `bin/game world bootstrap`, which called the Anthropic API via litellm (needs `ANTHROPIC_API_KEY`), is DEPRECATED under this policy: it still works but prints a deprecation notice, and shares the same validator + DB writer (`bootstrap_world` now calls `load_world` after its LLM call).

## Conventions

- Python venv at `.venv/`. Never `pip install` outside the venv (`PIP_REQUIRE_VIRTUALENV=true` is set globally).
- Python 3.10. Pin `requires-python = ">=3.10"` in `pyproject.toml`.
- User-visible services (the daydream FastAPI server) bind `0.0.0.0` so tailnet clients can reach them; default port `54321` (memorable, non-default, modest security-by-obscurity on a user-visible service). Override via `DAYDREAM_PORT`. Per-env ports land in v2.
- Internal services (vLLM, ComfyUI) bind `127.0.0.1` by default since daydream is their only consumer. Override with `DAYDREAM_VLLM_HOST` / `DAYDREAM_COMFYUI_HOST` to expose on the tailnet (e.g., for the ComfyUI web UI). For ComfyUI specifically, an SSH tunnel from your laptop is usually the right move: `ssh -L 8188:localhost:8188 <host>`.
- Persistent state lives under `~/data/daydream/`, never in the project tree. The active world is `worlds-dev/live.db`; per-env layout (`worlds-dev/`, `worlds-preview/`, `worlds-prod/`) lands in v2.
- HuggingFace cache is shared at `~/.cache/huggingface`. Never override `HF_HOME`.
- All `*.db`, `*.db-wal`, `*.db-shm` are gitignored. Live state never gets committed.

## Lifecycle

`bin/game up`, `bin/game deploy` (restart on current code, world preserved), `bin/game down`, `bin/game status`, `bin/game logs` are the supported daydream-server entry points; `bin/game comfyui-up`/`down` and `bin/game vllm-up`/`down` manage the inference engines (see "External engines" below); `bin/game image-test "<prompt>"` is the aesthetic A/B harness for image gen; `bin/game review` builds the offline batched-review contact sheet (see "Review & verification" below); `bin/game model-eval` is the LLM bake-off harness (see "vLLM (v1 LLM)" below). `bin/game up` is GPU-assuming by default: it runs a GPU preflight (free-VRAM check via `nvidia-smi`; floor `DAYDREAM_GPU_MIN_FREE_MIB`, default 9500 MiB) that exits with an actionable error if the GPU won't be available, then starts FastAPI synchronously and kicks off vLLM + ComfyUI in the background (engines warm over ~30-60 s; the game is reachable as soon as FastAPI's readiness poll completes). `bin/game up --no-gpu` brings up FastAPI only (CPU-only / docs / tests: no preflight, no engines). `bin/game up-all` is a back-compat alias for `bin/game up`. There is no symmetric `down-all`; `bin/game down` stops only FastAPI, so the engines need explicit `vllm-down` / `comfyui-down`. FastAPI's PID file and log live in `$XDG_RUNTIME_DIR/daydream-<env>/`; the shared engines' live in `~/.local/state/daydream/engines/` (they outlive a logout and serve every env); `bin/game status` reports liveness and reachability for all three processes plus the current `DAYDREAM_ACCESS` mode and a UFW-reminder warning when `public`.

Tests are tiered under a single entry point: `bin/game test {short,medium,long,ci,human}`. The durable contract (tier budgets, drift-loop semantics, adding a new test) lives in [`TESTING.md`](TESTING.md); read that before adding tests or bumping a model / LoRA / workflow. `bin/game test short` is the pre-commit gate (~10 s); `bin/game test long` runs the real-GPU drift probes under `tests/drift/` and compares against git-committed baselines at `tests/baselines/*.golden.json` (the baseline-update loop is the primary drift-detection mechanism, so a PR that changes a golden is a review event by design). The pytest-ified arbiter smoke replaces `tools/arbiter-smoke.py` as the authoritative source; the standalone script is still usable but reads the same probe corpus from `tests/drift/prompts/`.

### Coding turn vs. live server

Default: `bin/game down` before a coding turn. The server isn't required for any part of the dev loop: `bin/game test short/medium` boots its own TestClient against tmp state (`DAYDREAM_DATA_DIR` is overridden in `tests/conftest.py`), so nothing touches the live DB or the running server. Bring the game up only when you need to eyeball the SPA in a browser or demo something.

Safe to do with the game up:
- **Python edits.** uvicorn is NOT started with `--reload`; edits are inert until the next `bin/game up`. That's a feature: you can't accidentally half-apply a change.
- **Static asset edits** under `web/` (HTML, CSS, JS). FastAPI's StaticFiles re-reads from disk each request; a browser refresh picks up the change.
- **`bin/game test short` / `medium`.** Isolated via tmp data dir.
- **Commits, git work, file shuffling.**

Three reasons to bring it down first:
1. **`bin/game test long` while the game is up.** Each process has its own in-process gate; they coordinate only through the shared lock file (`/srv/daydream/data/gpu.lock`, present once prod is installed). Without it, concurrent image-gen from the server and pytest can OOM the 20 GB card.
2. **Migration work.** A new migration file is inert until `bin/game up` runs `init_live`. Control when it fires against `~/data/daydream/worlds-dev/live.db` by keeping the server down while iterating on the SQL. A wrong migration against live state means recovering from `~/data/daydream/archives/` or wiping and re-seeding.
3. **Schema / data-model refactors.** A connected WS session holds stale dataclasses (`Room`, `Toon`) in memory even after the DB has been migrated; the client sees pre-refactor shapes until restart. Confusing to debug.

**Agent automation policy for `bin/game up` / `down` (dev mode, enshrined 2026-07-01).** In dev, which is where this project lives today, the agent may `up` / `down` / `deploy` and take the GPU whenever tests or development work need it. Just grab it: no asking first. If a render, a `bin/game test long`, or a `bin/game review` pass wants the card, stop the server, do the work, and bring it back up. The one courtesy: a one-sentence note when you cycle it ("stopping the server to free the GPU for the forge render"), because a live browser session sees a brief disconnect (the calm "the dream is sleeping…" overlay, which recovers on its own). That's the whole cost, and in dev we don't care. This is a deliberate dev-mode stance so the agent isn't blocked on GPU work; a shared **preview/prod** deployment restores the ask-first, `git push`-category treatment (there the running server is someone else's live session). Default to leaving the server up when you're done unless there's a reason not to.

## Versioning & deploy staleness

Two staleness axes are surfaced/enforced so a stale process or world can't silently mislead (the "I thought we'd already redeployed" trap):

- **Code freshness (process vs HEAD).** The server captures its git short SHA at boot (`daydream/version.py:build_sha`; `DAYDREAM_BUILD_SHA` override; `"unknown"` off-git) and serves it at `GET /status/build`. `bin/game status` and the `bin/game up` already-up message compare it to the working tree's HEAD and print "N commits behind; restart to deploy". Every `state_snapshot` also carries the build; an open tab that sees it change (a redeploy under it, since a WS reconnect never reloads page JS: the cause of the forge id-garbage) auto-reloads ONCE into fresh assets (`web/assets/main.js`, behind a `sessionStorage` loop-guard). Asset URLs are `?v=<sha>`-stamped and `/assets/*` is `no-store` (`daydream/api/nocache.py`); together these close the stale-tab class.
- **World/content version (DB vs code).** `daydream/version.py:WORLD_VERSION` is a `MAJOR.MINOR` constant stamped into each world DB at `world load` (the `worlds.world_version` column, migration 012; the unused integer `schema_version` is a different thing). The server lifespan calls `version.check_world_compat` after `init_live`: a MAJOR mismatch REFUSES boot (the live world can't be carried forward) naming `bin/game world reset`; a MINOR or NULL (legacy) mismatch only warns. The gate is in the lifespan, NOT `db.init_live`: admin tools and the test suite call `init_live`, and blocking there would brick the very `world reset` that fixes a mismatch.

**Bump discipline.** Bump `WORLD_VERSION` MAJOR for a change that makes existing worlds unloadable (a non-additive migration, an objects-model change); MINOR for authored content/behaviour an old world won't reflect (a seed, a voice sheet, `worlds/lost-hours/`, a new verb); neither for code-only changes (a redeploy/restart already covers those). A refresh re-stamps the live world with the current version, so a MINOR bump followed by a refresh leaves no boot warning. (Last bumped to 1.5 for the pivot: The Village of Lost Hours and the story layer, 2026-09-26.) A dream patch does NOT bump it: dreams are additive changes to one live world, recorded in its `dream:applied:*` rows.

**APP_VERSION (the code's own release version).** `daydream/version.py:APP_VERSION` is the semver the RELEASE is called (1.0.0 as of the v1.0 turn), served as the `app:` line on `GET /status/build` and shown by `bin/game status`. It is pinned to `pyproject.toml`'s `version` by a drift-guard test (`tests/test_version.py`); bump both together at a release cut. Distinct from `WORLD_VERSION` (world CONTENT compat) and from the build SHA (which commit the process runs).

**`bin/game deploy`** is the everyday "make the running server match the code" verb: it restarts FastAPI on the current on-disk code (`down` then `up`) and PRESERVES the live world. Run it after committing/editing code you want live; the build-staleness line above is what flags a deploy is due. It briefly drops connected sessions, but a redeploy-aware client auto-reloads itself into the new build. An agent treats `deploy` as a shared-state action in the same category as `up`/`down` (it drops sessions): auto-run it only when the user asked to deploy/refresh or intent is clearly that, with a one-line note; otherwise ask.

**`bin/game world refresh [--check]`** is how an authored content fix reaches a played world: edit the sources, re-assemble, run `--check` (writes nothing), then refresh (snapshot, down, merge, up). It carries every authored definition (topics, voice sheets, rules, arcs, facts, storylets, config) into the live DB and inserts new authored objects, while keeping everything play wrote: players, positions, object state, arc progress, relationships, finds, deeds, grown rooms and their exits, and keys set by `property_set`/`mood_set` events. It re-applies every applied dream's `add` and `live` facts and cast additions, sends home what resting players hold, and re-stamps the world with the current WORLD_VERSION (`daydream/refresh.py`).

**`bin/game world reset --yes`** is the destructive runbook the boot gate points at: `down` → wipe `live.db*` + the world's image cache → `world load worlds/lost-hours.json --force` → `up`. A reset is a NEW village (day 0, no players, no dream history): use it for a MAJOR bump or a deliberate fresh start, never for a content fix (that is refresh). Take `bin/game world archive w-lost-hours` first if the live village matters, then `bin/game prebake` (server down) to paint it.

## Auth: accounts, invites, roles (SPEC 2026-09-27)

Everyone signs in with an account; there is no shared password and no network location that stands in for a login. Design record: `docs/GOING-LIVE.md` section 4.

- **Accounts live in `accounts-<env>.db`** (`config.accounts_db_path()`, migrations in `migrations_accounts/`), separate from the world DB, so a world reset, swap or refresh never touches them. `daydream/accounts.py` is the single read/write surface: argon2id passwords (the suite uses a cheap profile via `DAYDREAM_PASSWORD_HASH_PROFILE=test`); random 256-bit session tokens stored as sha256, read fresh on every request (revocation bites on the next request, and the WS re-checks on every frame); invites; throttles.
- **The sign-in gate** (`daydream/api/gate.py`) runs on every HTTP request and WebSocket and refuses anything outside the public allowlist (`/`, `/login`, `/healthz`, `/assets/*`, `/invite/*`, login, logout, invite peek/redeem) with a 401 (a 303 to the front door for an HTML navigation; a WS closed before accept). `tests/test_edge_access.py` walks every registered route to prove it, so a new route is guarded by default.
- **Cookie** `dd_session_<env>`: HttpOnly, SameSite=Lax, `Path=` the public base, Secure when the public origin is https, 30 days sliding.
- **Invites.** `bin/game invite create --for "Name"` mints a single-use two-word slug (`amber-thimble`, from `daydream/invite_words/`), sha256-stored, 14 days; `invite reset <user>` mints a set-a-new-password link; `invite list|revoke`. The link opens `web/door.html` (served for `/`, `/login`, `/invite/<slug>`), which redeems through `POST /api/invite/redeem`.
- **Roles.** `player` or `admin`, changed only from the CLI (`bin/game account role <user> admin`). In the browser an admin gets exactly three extras: the repaint tool, `/status/*`, and more than one toon. Everything that governs (invites, accounts, world ops, dreams, deploys, sleep/wake) is the CLI: **the shell is the admin console**. `bin/game account create|list|role|disable|enable|rename|sessions [--revoke]`.
- **CLI sessions.** Tools that talk to a running server mint a session in-process instead of logging in: `bin/game status` uses the CLI's own admin account (`account cli-cookie`, cached 0600), `bin/game play` and `tools/ws_*.py` use `agent-<name>` player accounts (`daydream.play.agent_cookie`). Make your own dev account once: `bin/game account create <you> --admin`.

## Session & presence

A few WS / slot-picker behaviors (`daydream/api/ws.py`, `daydream/api/slots.py`, `web/assets/main.js`) worth knowing before touching them:

- **Room descriptions on entry.** Every `state_snapshot` carries `room.description`; the SPA renders it into the persistent `#room-desc` header. On first entry to a room (when the replayed event log would be empty) the SPA ALSO synthesizes a look-style arrival line (`You are in X. You see: ...`) into the chat, so the log is never blank until you type `look` (client-only, `web/assets/main.js`; `look` is per-viewer, so the server never broadcasts it). Per-connection visit memory makes the header description the FULL stored `rooms.description_cached` on the first entry to a room this session and a short "you return to ..." line on re-entry (sticky for the visit so effect re-snapshots don't shrink it). Pre-baked stored text, never a live LLM call.
- **Fresh sessions.** A fresh page load opens `/ws` (no query) and gets an empty event log; a reconnect opens `/ws?since=<lastSeq>` and the server replays the room's missed events. Move/effect re-snapshots still carry the recent slice; a move's is also bounded to the room's last twenty minutes (`ws.ARRIVAL_REPLAY_S`), so hours-old ambient lines never read as happening now.
- **Reading the log (SPA).** New lines never leave the reading column starting mid-paragraph: `followLog` brings a line into view resting on a paragraph's top, an answer to the player's own action opens at its first line when taller than the column, a spacer (`#chat` padding) makes that reachable, and a reader scrolled back keeps their place unless they acted. Scrollable columns fade at an edge that holds more (`.more-above`/`.more-below`). Leaving the dream (or having no dreamer) shows the `awake` page, never an empty scene. `tests/test_browser_flow.py` holds all three in Chromium (playtest 2026-09-28).
- **Your dreamer (SPEC 2026-09-27).** A human toon belongs to one account (`objects.owner_account`, migration 018). A player account holds one toon per world and may enter, rest or delete only its own; an unowned toon (seeded, or from before accounts) can be adopted by an account that has none; admins may hold several toons, but act on another account's toon only from the shell (`bin/game world rest-toon|delete-toon <name>`), never from a browser session. `GET /api/dreamer` + `POST /api/dreamer/create` drive the SPA's "your dreamer" panel; `GET /api/slots` is the admin view; the slot-addressed POSTs remain for tools and tests. Human slots are 1..99 and internal.
- **Entry.** On WS connect, a session with no controlled toon that has not left the dream walks straight into its account's one toon (`ws._auto_enter`); otherwise it gets `{kind: "needs_toon"}` and the SPA shows "your dreamer". A second tab or device of the same account takes the toon over; the first socket gets `{kind: "elsewhere"}` and closes 4409 (the SPA shows a calm note and stops retrying). `POST /api/session/leave` rests the toon and marks the session left. There is no default-toon fallback.
- **Close codes and probes.** A refused handshake reads as 1006 in the browser, so the SPA's `onclose` asks `api/me`: 401 means the session lapsed (go to the front door); a 503 with `{asleep: true}` (the edge Worker's answer while the box is down) shows the sleep note and retries every 30 s.
- **Limits.** A typed line over 500 characters, or frames beyond a small per-connection token bucket, are refused with a `notice` frame and no effect (`ws.MAX_INPUT_CHARS`, `RATE_*`).
- **Toon delete.** `POST /api/slots/{slot}/delete` (`toons.delete_slot`) removes a toon and frees the slot: distinct from kick (rest). It DROPS the toon's carried items into its current room (they persist in the world to be found, not destroyed with the toon) and clears its memories; its events stay as append-only history.

## Objects, verbs, and the command bus

The MOO-style object/verb core (SPEC 2026-06-30). Foundational; read before touching `daydream/objects.py`, `verbs.py`, `parser.py`, `skills/effects.py`, or the WS input path.

- **One object store.** Migration 011 unified `rooms`/`toons`/`items` into a single `objects` table (`kind` in `room`/`toon`/`thing`/`prototype`). Containment is a self-referential `location_id` (a toon's location is its room; a thing's is the room or the carrying toon; a room is top-level). Inheritance is `prototype_id` → a `kind='prototype'` row whose `properties.verbs` are the default verb set. Promoted columns are only the toon auth/slot fields (`slot`, `controller_session`, `is_human_controlled`, `kicked_at`, and since migration 018 `owner_account`) + a partial unique index `(world_id, slot) WHERE kind='toon'`; everything kind-specific (seed, title, exits, appearance, mood, examined_text, ...) lives in `properties_json`. `daydream/objects.py` is the single read/write surface (`get`/`contents`/`in_scope`/`move`/`get+set_property`/`spawn`/`verbs_for`); `rooms.py`/`toons.py` are thin typed views over it, preserving their old APIs (`items.py` was removed in the v1.0 cleanup: use `objects.contents(room_id, kind="thing")`). No other module issues raw `objects` SQL.

- **Closed verbs + MOO dispatch.** `daydream/verbs.py` is a closed, engine-implemented verb set (`look`, `examine`, `take`, `drop`, `talk`, `ask`, `give`, `use`, `open`, `close`, `put`, `read`, `plant`, `say`, `go`, `inventory`, plus Zork's `attack`, `diagnose`, `board`, `disembark`; worlds declare more in data, e.g. Lost Hours' `wind`, `listen`, `sing`, `sit`, `wait`, `ring`, `pet`, `eat`, `drink`, `sleep`), each with an arg-spec (needs a dobj? an iobj? valid target kinds for each? per-verb effect allowlist? on the UI verb bar?). `execute_command(actor, verb, dobj_id?, iobj_id?, args?, dobj_name?)` is the single executor: it validates the dobj is in scope and the verb applies (`verb in objects.verbs_for(dobj)`: this rejects "take a toon" / "talk to a rock"), then dispatches by MOO priority (player → room → dobj → iobj). The one object-bound handler in v1 is an NPC's `talk` dialogue on the dobj, which beats the generic stub. Deterministic verbs make NO LLM call; only `talk` (dialogue) and a lazy-cache `examine` (below) do. `inventory` (no dobj) lists carried things. A named-but-out-of-scope target ("take the moon") is passed through as `dobj_name` so the executor reads "you don't see the moon here", distinct from the no-target "Take what?". The SPA mirrors verb-applicability client-side (staging a verb dims objects it can't target, so Talk never prompts on a non-toon), labels the scene (you / here with you / around you / you carry), and never shows object/toon ids in player-visible text (SPEC 2026-06-30).

- **Two-object verbs + object state (SPEC 2026-07-01).** `give` (dobj `thing` → iobj `toon`) and `use` (dobj `thing` → iobj `thing`) declare `needs_iobj` + `valid_iobj_kinds`; `execute_command` has an iobj gate symmetric to the dobj gate (missing/out-of-scope → "…to whom?/on what?", wrong-kind → refused, no mutation). `give` reparents a wanted gift onto the NPC, shifts mood, and spawns the NPC's authored `gives` reward into inventory (deduped by provenance). Object state is free-form `properties.state` (no migration), mutated only through the existing `set_property` effect: `open` is state-gated (`locked` refuses with authored `locked_text`; `unlocked`/`closed` → `open`, narrates `open_text`, reveals the `contains` payload once), `use` reads the target's authored `use` rule `{with, from_state, to_state, text}`, `read` narrates a readable's authored `text`, and `examine` appends `state_text[state]` to the physical seed. Both producers drive the two-object verbs: the parser fast-path grounds "give X to Y" / "use X on|with Y" (`parser._two_target_fast_path`), and the SPA does two-step click staging (stage verb → click dobj → click a kind-valid iobj). The canonical quest is The Village of Lost Hours' prologue; its walkthrough (`worlds/lost-hours/walkthroughs/prologue.json`, replayed in tier_medium) is the durable regression guard.

- **Two producers, one executor.** UI clicks send a `{kind:"command", verb, dobj_id?, …}` WS frame straight to `execute_command` (no parser, no LLM). Free text goes through the grounded parser (below) → `execute_command`. `take`/`drop`/`spawn` emit `object_moved`/`object_spawned`, which the broadcast loop treats as snapshot-refresh triggers so the scene/inventory panels update live.

- **Grounded local-LLM parser.** `daydream/parser.py` maps free text to one grounded command. A deterministic fast-path (exit directions, bare verbs, "verb \<in-scope-name>", legacy `rook hi`/`forge a ring` data-skill names) makes zero LLM calls. Otherwise one JSON-constrained Qwen call picks a closed verb + grounds the target to an in-scope **id** ("say hi to rook" / "talk to rook" / "greet rook" → `talk(t-rook, "hi")`; bare "say hi" → `say`). Unknown verb or out-of-scope/ambiguous target → verb `none` → a gentle "don't understand", no mutation. `say`/`talk` carry a `free_text` flag so the fast-path defers their args to the LLM (say-vs-talk).

- **LLM is a hard runtime dependency.** "The dream is foggy" is an OUTAGE message, not a play mode. When vLLM is down, natural-language free text degrades to foggy, while deterministic click/exit verbs (examine-of-cached, take, drop, go) still work. The `bin/game up` GPU preflight is the startup guard. (Consistent with the generation policy: still local-only, no cloud key.)

- **World-mutation effect API.** `daydream/skills/effects.py` is the allowlisted vocabulary ALL runtime mutation flows through: `narrate`, `set_property`, `spawn_object`, `move_object`, `spawn_room`, `link_exit`, `rename_object` (with `add_item`/`set_mood` retained as aliases for existing data-skill author files). `dispatch_effects(..., allowed=<subset>)` enforces a per-verb allowlist: a kind outside it is rejected like an unknown kind (no mutation). The RESTRICTED kinds (`spawn_room`/`link_exit` world-shaping + `rename_object` housekeeping + `set_property`, the arbitrary property write) are per-verb OPT-IN only: `allowed=None` (the data-skill default) resolves to `DEFAULT_KINDS`, which excludes them, so an NPC dialogue or standalone data skill can never world-build, rename, or write an arbitrary property; `plant` is the sole consumer of the world-shaping kinds and `rename_object`. `set_property` (any key, any JSON value, on any object) is off `talk`'s allowlist and the data-skill default; engine verbs that write authored state (e.g. `examine`, `open`, `use`, `plant`) and authored rules (`RULE_KINDS`) declare it, while dialogue mood changes use the string-validated `set_mood` (codereview WARN 2026-09-26b). `destroy_object` is BUILT (the Zork turn): rule-only kind; contents drop to the holder's location; combat's death path is its main consumer.

- **Dreamseeds / world growth (SPEC 2026-07-02).** The quest-earned dreamseed in the clock case is the growth permission: `plant` it with a short vision phrase and `daydream/growth.py` runs gates (carried → unspent → has `properties.growth` → cap `DAYDREAM_GROWTH_MAX_ROOMS` (default 12, counts only grown rooms) → free compass direction → phrase ≤120 chars + banlist; empty phrase narrates the seed's authored question) → ONE local-LLM call (the dream-gardener prompt: seed boundaries + exemplars, no ids/directions ever shown to the model) → strict validation (schema windows, 0–2 objects reject-not-truncate, WHIMSY banlist, anti-copy vs the seed's exemplars, refusal escape hatch) → a SYNCHRONOUS commit block that re-checks every raced gate, then dispatches spawn_room → link_exit → spawn_object(s) → seed consumption (state `spent`, husk examine, verbs cleared, moved into the grown room) → payoff narrate naming direction + title. Every failure path preserves the seed and mutates nothing. Grown rooms are first-class (provenance `generated_by="plant:<seed-id>"` + structured `grown`; lazy watercolor art on first entry; walkable exits both ways). The authored growth boundaries live in the canonical world's `config.templates.dreamseed` (`worlds/lost-hours/world.json`; the design-time pre-bake: theme/palette/motifs/exemplars/skeletons validated fail-loudly by the loader); the real-GPU composition probe is `tests/drift/test_growth_compose.py` (tier_long), whose golden ratification records the mitigation-ladder rung. **Propagation (SPEC 2026-07-07): the growing-world loop.** A seed whose `growth.propagation` block (chance in (0,1], max_generation 1-4, optional seed_text; loader-validated) survives can, on a successful plant, spawn a fresh plantable dreamseed inside the newly grown room: same commit batch, FIRST among the spawns (so the generative dedup can't eat it), boundaries inherited verbatim with `growth.generation`+1, provenance `propagation:<parent-seed-id>`. The roll is `worldstate.rng(world_id, "seed-propagation:<new-room-id>")`: deterministic; suppressed at generation >= max_generation and at the grown-room cap counting the plant's own room; a malformed runtime block means no propagation, never an exception; zero new LLM surface. **First-planting chapter close:** `growth.first_planting_text` (optional, loader-validated) narrates once when the world's FIRST room grows and lands in the planter's journal via `journal.append_authored`; a worldstate `first_bloom` marker is the re-fire belt. Explicitly not a `win`.

- **Generative objects.** (Legacy data-skill dialogue and growth; voice-sheet dialogue never spawns.) Promotion is by EXPLICIT declaration only: narration is never auto-scanned for nouns. An object becomes real when a verb's LLM output emits a `spawn_object` effect (Rook's "sheaf of papers"); generative spawns dedup on name+location+provenance so re-running the verb never duplicates. `examine` is lazy-cache: a spawned object with no seed and no cached text gets ONE LLM call, persisted as `properties.examined_text`, then served from cache (zero LLM) thereafter; seeded objects stay deterministic. Provenance (`generated_by`) + an `ephemeral` flag are in place for the future clutter-GC pass (no GC today).

- **NPC dialogue binding.** `talk`'s dialogue is resolved by `verbs._bound_dialogue_skill`: the NPC's `properties.dialogue` (a data-skill name) first, else the legacy `t-<name>` convention (seeded Rook/Iris). `load_world` installs per-NPC dialogue from the envelope's `toons[].dialogue` as a hidden data skill (a sentinel `context_predicate` keeps it out of room-affordance lists; `talk` reaches it directly) and sets `properties.dialogue`. This is the legacy (format-1) path: the canonical world's NPCs carry a voice sheet instead and talk through `daydream/dialogue.py` (see The story layer below); `worlds/bunny.json` (Rook/Iris/Bram) is retained in-repo as the `tests/test_scenario.py` loader fixture (old-style envelope → backward-compat coverage). The loft envelope was retired 2026-09-26 (recoverable from the `pre-pivot` tag).

Only waking from rest starts a player at the start room; re-claiming a toon that never rested keeps it where it stands.

A composition that is a near-copy of an exemplar (60% or more of its description's words) is rejected, and a rejected composition gets one more warm try.
- **The parser keeps an utterance whole.** Periods and THEN split only command chains; `say ...` and `talk to X[:] ...` resolve deterministically; one-letter aliases act only alone; "look through / out of / into X" examines X.

## Network access

`DAYDREAM_ACCESS` (default `tailscale`) is the network rule in `daydream/api/access.py`, layered UNDER account sign-in. No mode grants a session:

- **`tailscale`** (dev): admits tailnet (`100.64.0.0/10`) and loopback peers; others get 403 / WS close 1008.
- **`edge`** (prod, behind the Cloudflare Worker + tunnel): admits loopback peers only (cloudflared is the only way in), compares CSRF Origin to `DAYDREAM_PUBLIC_ORIGIN` (Host is the tunnel hostname there), takes the client address only from the Worker's `X-Daydream-Client-IP`, and has no world-swap endpoint. `DAYDREAM_ENV=prod` refuses to boot in any other mode or without an https public origin, an explicit `DAYDREAM_PUBLIC_BASE` and a loopback `DAYDREAM_BIND_HOST` (`config.boot_problems`).
- **`public`**: no network filter (the test suite). This project never opens UFW for daydream.

**The rule: no network location grants privilege.** Loopback is not an admin boundary (a tunnel connects from loopback). Admin surfaces check the account role; `/api/world/swap` additionally requires a loopback peer and does not exist in edge mode.

Middleware order per request: security headers (CSP, nosniff, no framing, noindex; `daydream/api/headers.py`) > access (network) > CSRF > gate (account) > no-cache assets > app. The SPA is base-relative (`<base href>` from `DAYDREAM_PUBLIC_BASE`; `tests/test_web_paths.py` fails on a root-absolute path in `web/`), so the same build serves at `/` in dev and under `/daydream/` behind the Worker, which strips the prefix before proxying.

It holds no secrets. It is NOT enabled at boot; nor is `cloudflared-daydream.service`. A narrow sudoers entry lets the operator (and so a Claude session) start/stop/restart exactly these units.

A path under the operator's home is refused (the service user can't read it): a dream reaches prod committed and deployed. Art for prod is the graded dev art: `bin/game prod prebake --from-cache ~/data/daydream/images/cache`.
- **The server's log** (`daydream/logs.py`, configured in the lifespan; `DAYDREAM_LOG_LEVEL`, default INFO): sign-ins, invitations, dreamers, WebSocket sessions with their length, model calls (`daydream.llm.usage`), paintings, journal outcomes, and session errors with tracebacks reach the journal (`bin/game prod logs`) or dev's run-dir log. Lines carry accounts, dreamers, ids and timings only: never a password, a token, an invite slug or typed text (`tests/test_logs.py`).
- **`bin/game edge <verb>`** (`daydream/edge.py`): `status`, `sleep [note]`, `wake` (the KV flag only), `deploy`, `secrets`, `kv-create`, `tail`, `test`. Credentials: `~/.config/daydream/cloudflare.env` (0600).
- **Agent policy for prod (operator's standing grant, 2026-09-28).** Dev keeps its grab-the-GPU autonomy. The operator wants the agent to drive prod from this repo: when the operator asks for prod work (deploy, rollback, wake, sleep, world ops, dream install, accounts, invites, edge deploy/sleep/wake), the agent runs the verbs itself with a one-line note per step, and does not hand commands back. The local rule in `.claude/settings.local.json` lets them run without a prompt, except the verbs that mint a credential or a privilege or replace the world (`prod invite reset`, `prod account role|create|cli-cookie`, `prod world reset|delete|restore|snapshot-restore|restore-backup|load`), which always prompt: player text reaches the agent's context, and those are the verbs an injected instruction would want (SECURITY NOTE 2026-09-28). Unasked, a verb that drops sessions or changes prod data still asks first; `prod status`, `prod logs` and `prod invite create|list` never need to. Only root-owned files (`/srv/daydream/etc/prod.env`, `/etc/cloudflared/`) and the Cloudflare dashboard need the operator's hands. Never mend the prologue clock with the operator's account in prod: the first friend gets that moment.
- **The operator is "the Night Warden"** to players: `DAYDREAM_OPERATOR_NAME` in `prod.env` and `OPERATOR` in `edge/wrangler.toml` carry that title, and every player-facing surface prints it verbatim ("Send the Night Warden a note and the lamps will be lit"). Never the operator's name. Unset, both fall back to "the person who invited you". Canon: the title lives only outside the story (`docs/canon/LOST-HOURS.md` section 1).
- **The deploy gate runs while prod is awake.** `prod deploy` runs short + medium in a throwaway worktree that borrows the dev venv, so a test that shells out to `bin/game` must not depend on the box's prod state (the `bin/game` smoke test sets `DAYDREAM_ALLOW_GPU_WITH_PROD=1` because the suite blanks `DAYDREAM_GPU_LOCK`).
- **GPU sharing.** Dev and prod share one vLLM and one ComfyUI (engine PID/log files live in `~/.local/state/daydream/engines`, and `vllm-up`/`comfyui-up` no-op when the engine already answers). The arbiter's cross-process layer (an flock on `/srv/daydream/data/gpu.lock`, `config.gpu_lock_path()`) makes every daydream process on the box (dev, prod, a `test long` run) obey the same rule: a render never overlaps an LLM call or another render anywhere; a render that cannot get the card within 20 s gives up and keeps its placeholder. On a box without that lock file, GPU-heavy dev commands refuse while prod is awake (`DAYDREAM_ALLOW_GPU_WITH_PROD=1` overrides).

## GPU posture

20 GB VRAM ceiling on this box (RTX 4000 SFF Ada, compute capability 8.9). vLLM (Qwen3.5 9B AWQ 4-bit, ~7.5 GB resident) and ComfyUI (SDXL base + watercolor LoRA, ~6 GB resident, ~10-12 GB peak during inference) coexist behind the arbiter at `daydream/gpu/arbiter.py`: a shared/exclusive gate (v2, 2026-07-02; mirrored across processes by an flock since 2026-09-27): LLM calls take shared slots and run CONCURRENTLY up to `DAYDREAM_LLM_CONCURRENCY` (default 3; vLLM batches natively inside its preallocated slice, so concurrency costs KV tokens, not extra VRAM), while every image render takes the exclusive slot and runs alone. Admission is text-priority: a queued LLM call is admitted before a queued render (renders lazy-paint; text is a player waiting). Observability: `GET /status/arbiter`, surfaced in `bin/game status`. All LLM calls flow through `daydream/llm/client.py` (acquires `"llm"` internally) and all image-gen through `daydream/images/client.py` (caller wraps in `arbiter.acquire()`) so the gate has exactly two call sites.

This project assumes Daydream is the only GPU consumer on this box. The `qwen-2.5-localreview` warm server is off (per its `.env`) and is assumed to stay off indefinitely; no external process competes for VRAM. The arbiter therefore needs only in-process coordination (an asyncio gate is sufficient; flock is still a fine code template at `~/src/qwen-2.5-localreview/gpu_lock.py`).

**Full narrative: VRAM math, model selection rationale, things we tried and rejected (the fp8-KV story especially), things to try later: lives in [`docs/gpu-and-models.md`](docs/gpu-and-models.md).** Read that before bumping a model, swapping an engine, or adding a tuning flag.

## External engines

External engines that daydream calls over HTTP but does not vendor as code (ComfyUI, vLLM, future image-gen / LLM backends) follow one pattern so the project tree stays self-contained on disk while staying git-light:

```
external/<engine>/         # upstream repo, gitignored; cloned by bootstrap
external/<engine>/.venv/   # the engine's own python venv (separate from daydream's .venv)
external/<engine>/models/  # large model files where the engine expects them
```

Each engine gets:
- `bin/<engine>-bootstrap`: idempotent: clone if missing, venv if missing, pip install requirements, download model files. Re-runs are no-ops on every step. Safe to invoke whenever you're not sure if it's installed.
- `bin/game <engine>-up` / `<engine>-down`: daemon lifecycle, mirroring `bin/game up` / `down` for FastAPI. PID file under `$XDG_RUNTIME_DIR/daydream-<env>/<engine>.pid`, log alongside.
- `bin/game status`: shows the daydream-managed PID when up; falls back to a reachability probe so externally-launched instances are still detected.
- A config function in `daydream/config.py` (e.g. `comfyui_base_url()`) that returns the endpoint, overridable via env var, so daydream Python code never hardcodes `localhost:<port>`.

`bin/game up` starts the engines in the background after its GPU preflight (see Lifecycle); `bin/game up --no-gpu` is FastAPI only, and `bin/game up-all` is a back-compat alias for `up`. The engines stop only with explicit `vllm-down` / `comfyui-down`. Daydream's graceful-failure paths (`narrate "the dream is foggy"` for LLM down, "painting..." overlay for ComfyUI down) mean the game still runs at every engine combination.

`external/` is gitignored entirely. No submodules, no nested .git tracking: bootstrap re-creates the whole thing from a single command, so losing it is cheap.

### Pattern exception: HF cache

Engines that use HuggingFace's model hub (vLLM is the obvious case) put their model files in `~/.cache/huggingface/hub`, NOT under `external/<engine>/models/`. The shared HF cache is a zat.env convention (never override `HF_HOME`) and trumps the per-engine self-containment when the two collide. Bootstraps for HF-backed engines pre-cache via `huggingface_hub.snapshot_download` so first-launch is fast.

ComfyUI does NOT use the HF cache (its `models/` dir lives under `external/ComfyUI/`); vLLM does. Future engines decide case by case.

### Pattern exception: foreground engines (qpeek)

Not every external engine is a daemon. `qpeek` (the human-aesthetic-eval engine used by `bin/game test human`) is a **foreground** process: `bin/qpeek-bootstrap` clones and installs like every other engine, but there is no `bin/game qpeek-up/down` and no PID file: `bin/game test human` invokes qpeek directly as a blocking subprocess and parses the JSON rating array from its stdout. Design reason: qpeek is transient by nature (human-interactive, one-shot per review). Forcing it through a daemon lifecycle would add complexity the use case doesn't need.

## ComfyUI (v1 image gen)

The first engine on the pattern. Binds `127.0.0.1:8188` by default since daydream is the only consumer; override `DAYDREAM_COMFYUI_HOST=0.0.0.0` to expose on the tailnet (e.g., for the ComfyUI web UI from another machine), or SSH-tunnel: `ssh -L 8188:localhost:8188 <host>`. Override the URL daydream calls with `DAYDREAM_COMFYUI_BASE_URL` or the port via `DAYDREAM_COMFYUI_PORT`.

One-time install:

```sh
bin/comfyui-bootstrap        # clones, venv, pip install, downloads SDXL + LoRA (~10 min, ~13 GB)
```

Daily lifecycle:

```sh
bin/game comfyui-up          # start daemon (PID owned by daydream)
bin/game comfyui-down        # stop daemon
bin/game status              # shows pid + reachability when running
```

The shared workflow JSON at `daydream/images/workflows/painterly_room.json` is read by both `daydream/images/client.py` (room backgrounds) and `daydream/images/cli.py` (`bin/game image-test`). The current pick is SDXL base 1.0 + `ostris/watercolor_style_lora_sdxl` (`watercolor_v1_sdxl.safetensors`); to swap, edit `lora_name` in the workflow and both call sites pick it up. Use `bin/game image-test "<prompt>" --lora <new>.safetensors` for cheap A/B before committing the swap.

## vLLM (v1 LLM)

The second engine on the pattern. Different from ComfyUI in that vLLM is a pip package (no upstream clone), and its model weights live in the shared HF cache (per the exception above). Binds `127.0.0.1:8000` by default since daydream is the only consumer; override `DAYDREAM_VLLM_HOST=0.0.0.0` to expose on the tailnet. Override the URL daydream calls with `DAYDREAM_LLM_BASE_URL` or the port via `DAYDREAM_VLLM_PORT`. Default model is Qwen3.5 9B AWQ 4-bit, `cyankiwi/Qwen3.5-9B-AWQ-4bit` (`DAYDREAM_VLLM_MODEL` to override; `DAYDREAM_LLM_MODEL` for the client side).

One-time install:

```sh
bin/vllm-bootstrap           # venv, pip install vllm, pre-cache Qwen3.5 9B AWQ (~9 GB)
```

Daily lifecycle:

```sh
bin/game vllm-up             # start daemon (PID owned by daydream)
bin/game vllm-down           # stop daemon
```

`bin/game vllm-up` launches with `--gpu-memory-utilization 0.45` (~9 GB on the 20 GB card) leaving headroom for SDXL during inference. Both daemons can stay resident under the arbiter; concurrent LLM calls batch inside vLLM's preallocated slice while an image render runs exclusively, so the VRAM peak is bounded by (residents + one render's working set), never two engines inferencing at once. `--max-model-len 8192` is the default context window; increase if v2 long-context needs warrant it (raises KV cache memory). `--max-num-seqs 4` (`DAYDREAM_VLLM_MAX_NUM_SEQS`) caps engine-side batch concurrency: it must be >= `DAYDREAM_LLM_CONCURRENCY` (default 3) because a timed-out client abandons a request that keeps decoding server-side, so the engine cap (not the app's arbiter admission) is the true bound. The KV pool at 0.45 is ~21k tokens (Qwen3.5's hybrid attention keeps KV in only a quarter of its layers, so a smaller pool still holds 2.5 full 8192-token contexts); real calls peak around 1.1k tokens (a Zork-scale parser prompt), so 4 concurrent calls use ~4.5k. See docs/gpu-and-models.md.

daydream calls vLLM through `daydream/llm/client.py` via `litellm.acompletion` against the OpenAI-compatible endpoint, all wrapped in `daydream.gpu.arbiter.acquire("llm")` so text shares the GPU under the arbiter's cap and never overlaps an image render.

### vLLM tunings on Ada

These flags ride on every `bin/game vllm-up`. They were re-measured in the September 2026 bake-off (`bin/game model-eval`; docs/gpu-and-models.md "September 2026 re-evaluation") on top of the earlier `~/src/qwen-2.5-localreview` experiments on this same card. Treat them as load-bearing: don't change one without re-running `bin/game model-eval run` (scores + per-surface latency) and `tools/arbiter-smoke.py`. Full rationale per flag lives in [`docs/gpu-and-models.md`](docs/gpu-and-models.md).

| Flag | Why |
|---|---|
| `--language-model-only` | Qwen3.5 is vision-language; this loads only the text tower (7.55 GiB). Harmless on a text-only model (verified with the Qwen 2.5 rollback). |
| `--default-chat-template-kwargs '{"enable_thinking": false}'` | Qwen3.x reasons before answering by default. Every daydream call wants the answer only; set server-side so `daydream/llm/client.py` stays model-agnostic. |
| CUDA graphs on (no `--enforce-eager`) | The old 0.19-era OOM reason is gone: vLLM >= 0.21 profiles graph memory before sizing KV (graph pool ~0.03 GiB). ~10% lower latency on the hybrid 9B; none on a dense 7B. Re-add via `DAYDREAM_VLLM_EXTRA_ARGS=--enforce-eager` if a capture OOM ever returns. |
| `PATH` includes the vLLM venv's `bin/` | FlashInfer JIT-compiles kernels with `ninja`, which lives in the venv; off `PATH` the engine dies at startup. |
| `VLLM_LOGGING_LEVEL=ERROR` | Suppresses vLLM's verbose startup banner. Override with `VLLM_LOG_LEVEL=INFO bin/game vllm-up` when debugging. |
| `VLLM_HOST_IP=127.0.0.1`, `GLOO_SOCKET_IFNAME=lo`, `NCCL_SOCKET_IFNAME=lo` | Pin the EngineCore's internal torch-distributed sockets to loopback. Unpinned, Gloo binds to the hostname's address, which on this box resolves to the PUBLIC IPv6 first (six high ports guarded only by UFW, found 2026-09-27). `tests/drift/test_drift_constants.py` pins the exports. |
| `vllm==0.30.0` (pinned in bootstrap) | >= 0.20 is required for Qwen3.5's Gated DeltaNet layers. A pin change REBUILDS the venv (the stale one is moved to `external/vLLM/.venv.stale-*`, the rollback copy): an in-place upgrade left a CUDA 12 runtime and a mismatched flashinfer-cubin behind. |

`DAYDREAM_VLLM_EXTRA_ARGS` appends raw flags for experiments. The default model is a community upload, so `bin/game` and `bin/vllm-bootstrap` pin it to the commit the bake-off measured (`--revision`, which also pins the tokenizer); the pin applies only to the default model, `DAYDREAM_VLLM_REVISION` overrides, and a tier_short drift test keeps the two scripts' pins identical. `bin/game vllm-down` waits for the `VLLM::EngineCore` child to exit, not just the API server: at the 0.45 slice the 9B's KV budget is only ~0.9 GiB, so a `vllm-up` that starts while the old engine still holds memory fails with "No available memory for the cache blocks". Rollback to the previous model is `DAYDREAM_VLLM_MODEL=Qwen/Qwen2.5-7B-Instruct-AWQ` + `DAYDREAM_LLM_MODEL=hosted_vllm/Qwen/Qwen2.5-7B-Instruct-AWQ` (runs on the same launcher and engine).

**Model choice (Qwen3.5 9B AWQ 4-bit, since 2026-09-26).** It won the bake-off against Qwen 2.5 7B (the prior pick), Qwen3 8B/14B, Gemma 4 12B and Qwen3.5 4B: parser grounding 47/48 vs 41/48, zero NPC point-of-view slips, blind-graded prose +0.69 on a 5-point scale (95% CI 0.41-0.97), all inside the UNCHANGED 0.45 slice (peak 17.1 GB with an SDXL portrait render). The cost is latency: dialogue p50 ~2.7 s vs ~1.5 s, parser ~1.0 s vs ~0.6 s. Qwen3 14B scored as well but leaves ~0.65 GB free during a portrait render; Gemma 4 12B wrote the best rooms but ran long and slow. The 2026 Qwens carry a 248K vocabulary whose embeddings stay BF16 under AWQ, which is why a "4-bit" 9B weighs ~7.5 GiB.

### `--kv-cache-dtype fp8_e4m3` deliberately NOT enabled

Localreview gets a documented **+58% decode TPS / ~0.9 GB freed VRAM** from FP8 KV cache on their 14B Coder with long (32K) contexts. On our workload it has never paid:

- **Qwen 2.5 7B (2026-05):** deterministically broke tight-format JSON adherence (the model looped `!***` garbage tokens).
- **Qwen3.5 9B (2026-09-26):** no quality regression, but no latency gain either. Our prompts are ~1k tokens, so decode bandwidth is dominated by weights, not KV. Its larger startup workspace also fails to boot beside a resident SDXL at 0.45.

Revisit only if prompts grow to multi-thousand-token contexts (long NPC memory, whole-room histories), where KV reads start to dominate. Verify with `bin/game model-eval run` plus a co-resident boot.

## NPC memory

Per-world NPC dialogue memory at `daydream/memories.py`. `capture(npc_id, world_id, text, source_event_seq=None)` and `retrieve(npc_id, world_id, query, k=3)` are sync, fail-closed (None / [] + log on any failure), and CPU-only: they never take the GPU arbiter. Embeddings via `sentence-transformers` BGE-small (`BAAI/bge-small-en-v1.5`, 384-dim) on CPU, lazy-loaded on first call, stored as raw float32 BLOBs in the per-world `memories` table (migration 009). Retrieval ranks by `cosine_similarity * exp(-age_hours / 24)`; the constant lives in `DAYDREAM_MEMORY_DECAY_HOURS`. v0 deliberately keeps it SQLite-only; LanceDB is the v1 path once memory counts cross ~10K per NPC.

Voice-sheet dialogue (the canonical world) does NOT use this memory: its continuity is the per-player recent exchanges (`talk:<npc>:<toon>`) and the knowledge facts. Only legacy data-skill dialogue and drift variation retrieve. The data-skill pipeline (`daydream/skills/data.py`) calls `retrieve` before Jinja render (the `memories` template variable is always present, possibly `[]`) and `capture` after a successful narrate-effect dispatch. Skill-name → NPC-id mapping is `f"t-{skill_name}"`; skills with no matching NPC row (e.g., `forge`) skip both phases.

One-time setup: `bin/memory-bootstrap` installs `sentence-transformers` against the PyTorch CPU wheel index (~200 MB vs ~2 GB for default CUDA wheels) and pre-caches BGE-small in the shared HF cache. Idempotent; skip-if-present. Bootstrap is optional: the dialogue path keeps working without it (capture/retrieve fail closed and NPCs just have no memory). Toggle via `DAYDREAM_MEMORY_ENABLED` (default `1` in production; `0` in `tests/conftest.py`); tests that exercise memory monkeypatch `daydream.memories._embed` to inject deterministic vectors so the suite never loads the real model.

## Image generation API

Single entry point: `daydream.images.client.generate_image(target, *, model=None, lora=None, seed=None, base_url=None) -> Path`. The target is a discriminated union (`PersistentTarget` or `EphemeralTarget`) and the persistent vs ephemeral distinction lives there as a first-class concept rather than as two parallel functions.

**`PersistentTarget(world_id, target_kind, target_id, seed, prompt_suffix="")`** is bound to an in-world entity (a room, in v1; toons / items later via `target_kind`). Output lands at `images/cache/{world}/{kind}/{id}/{combined_hash}.png` where the combined hash folds in seed text + canonical workflow JSON. On cache miss: render, write, record to `generated_assets`. On cache hit: return immediately, no re-record. Recording is REQUIRED here: if the DB isn't initialized, the call raises (production WS path always has DB initialized; this catches programming bugs).

**`EphemeralTarget(name, prompt, with_whimsy_suffix=True, out_path=None)`** is for one-off output: aesthetic A/B, debugging, scratch. Output lands at `images/ephemeral/{safe_name}-{prompt_hash}.png` (deterministic per prompt so re-runs overwrite, which is what A/B work wants). Never recorded. Works with no DB initialized: the `bin/game image-test` CLI takes this path.

Both paths share the same workflow build, the same ComfyUI HTTP layer (`_execute_workflow` is the single mock point), and the same arbiter contract: callers MUST hold `daydream.gpu.arbiter.acquire()` for the duration of any `generate_image` call. The two callers in production (WS layer, image-test CLI) do this; `tools/arbiter-smoke.py` does it; tests bypass via `@pytest.mark.real_image_gen` and mock `_execute_workflow`.

## Generated assets

Every persistent generation lands a row in the per-world `generated_assets` table. The table is the durable provenance index over the cache layout: given a world, you can answer "what was generated, with which model + LoRA + workflow, from which prompt, how big on disk, when?" without scanning the filesystem.

**File layout:**
```
~/data/daydream/
  worlds-{env}/live.db                                # per-env DB; holds generated_assets
  images/cache/{world}/{kind}/{id}/{combined_hash}.png   # persistent output
  images/ephemeral/{safe_name}-{prompt_hash}.png      # ephemeral output (no row)
  archives/{world}-{ts}.tar.gz                        # bin/game world archive output (full bundle)
  snapshots/{world}-{ts}.db                           # bin/game world snapshot output (DB-only)
```

The cache key `combined_hash = sha256(seed_hash + workflow_hash)` so editing the seed OR the workflow JSON (sampler tweaks, LoRA strength, resolution) busts the cache and triggers regen. The recorded `workflow_hash` column lets you query "which assets came from which workflow version" later. The `target_kind` segment in the path prevents slug collision when NPC portraits land alongside room backgrounds.

**Schema (per-world):** `id, asset_kind, target_kind, target_id, target_seed, seed_hash, file_relpath, model, lora, prompt_text, generated_at, file_bytes, world_id, pinned, workflow_hash`. The `pinned` column is the future-GC escape hatch: a hero image that should never be auto-cleaned can be marked via `assets.pin_asset(id)`. Used by zero code today; in place so the first gardening pass needs no migration.

**Operator commands** (all under `bin/game world`, dispatch via `daydream/admin.py`):

```sh
bin/game world list                              # worlds + per-world asset count + cache footprint
bin/game world archive <world_id>                # checkpoint WAL, tar DB + cache + manifest → archives/
bin/game world restore <archive.tar.gz> --yes    # validate manifest, untar into data_dir (refuses if live DB exists)
bin/game world snapshot <world_id>               # checkpoint WAL, copy live DB → snapshots/{world}-{ts}.db (DB-only, no cache/manifest)
bin/game world snapshot-restore <snap.db> --yes  # install a snapshot as the live DB (refuses to overwrite; refuses newer schema)
bin/game world swap <target.db>                  # LIVE hot-swap the running server's world to target.db (no restart; clients re-snapshot)
bin/game world verify [world_id]                 # report orphan rows (file missing) + orphan files (no row)
bin/game world delete <world_id> --yes           # cascade DELETE rows (filtered by world_id) + rm -rf cache dir
bin/game world load <envelope.json>              # KEYLESS: build a world DB from an Opus-authored JSON envelope (no API key)
```

`archive` runs `PRAGMA wal_checkpoint(TRUNCATE)` before the tar so a hot DB's most recent transactions are captured (without this, anything in `live.db-wal` would be missed). It writes a `MANIFEST.json` to the archive root recording `archive_format_version`, `schema_version`, `world_id`, `asset_count`, `asset_bytes`, `created_at`. `restore` validates the manifest before extracting; refuses archives produced by a newer schema than this code knows about, and refuses to overwrite an existing live DB.

`verify` is diagnostic only: it never deletes. Reports two kinds of inconsistencies: rows whose `file_relpath` no longer exists on disk, and PNG files in the cache dir that have no matching row. Both happen naturally: the legacy meadow PNG from before this turn's cache layout change is exactly an orphan-file. Future GC tooling will read these reports.

**Extending to other asset kinds.** The schema's `asset_kind` (`'image'` for now) and `target_kind` (`'room'`, `'toon'`, `'item'`) columns are the extensibility hooks. NPC portraits land as `target_kind='toon'` rows, no migration needed. Regenerated text outputs (e.g., room descriptions written back into `rooms.description_cached`) would be `asset_kind='text'` and need a small schema relaxation (`file_relpath` becomes nullable; an inline-text column joins it). That's the next migration whenever LLM-driven text caching becomes load-bearing.

**`snapshot`/`snapshot-restore` vs `swap` vs `archive`/`restore`.** `snapshot` (above) is the fast, DB-only point-in-time copy: the sqlite online-backup API writes just the `.db` to `snapshots/{world}-{ts}.db`, consistent even while a server writes (`backup` does the same for the world + accounts DBs into `backups/<ts>/`, rotating): no per-world cache, no `MANIFEST.json`, no tarball. `snapshot-restore` installs such a file as the live DB OFFLINE: it refuses to overwrite an existing live DB and so requires the server down. `swap` is the ONLINE counterpart: it talks to the running server's `POST /api/world/swap` (an admin session plus a loopback peer; absent in edge mode; its only real client is `bin/game world swap` on-box, signed in as the CLI's admin account; see SECURITY.md) (the offline CLI cannot reach the in-process live connection / drift task), which stops drift, performs a synchronous-and-therefore-atomic close+install+reopen of the live connection onto the target (`daydream/db.py:swap_live_db`, failure-safe: a failed swap restores the original world), restarts drift, and broadcasts a `WORLD_CHANGED` control signal (`daydream/events.py`) so each connected WS client re-snapshots against the new world. Both restore paths read the target's own `_migrations` table and refuse a newer-than-known schema. `archive`/`restore` is the heavyweight bundle: full DB + per-world cache + manifest, suitable for shipping a world to another box. The SPA shows a brief "the dream shifts…" overlay on the `WORLD_CHANGED` signal, cleared by the fresh `state_snapshot` that follows (the calm connection-state overlay in `web/assets/main.js`, shared with the "the dream is sleeping…" reconnect state, SPEC 2026-06-30); re-picking a toon absent from the new world remains a smaller follow-up.

Cozy, soft, painterly. Spiritfarer / A Short Hike. NOT pixel art, NOT crunchy 8-bit. Bake this into placeholder PNGs and any narration prompts. ## Tests

`pytest` from the project root. Tests must not require GPU or a running vLLM; mock the LLM client. `tests/test_browser_flow.py` (tier_medium) drives the real front door in headless Chromium, and `tests/test_layout_screens.py` checks layout rules (nothing sideways, the door's form reachable, the shell's foot clear of the bottom) over a screen matrix in Chromium, Firefox and WebKit (`DAYDREAM_LAYOUT_SHOTS=<dir>` saves each stop; TESTING.md); it needs a one-time `.venv/bin/python -m playwright install chromium-headless-shell` and skips cleanly where the browser is absent (CI). The ops files and the playbooks are tested against the code (`tests/test_ops_units.py`, `tests/test_runbooks.py`): renaming a prod verb fails the build until the playbooks follow. Slow/integration tests that boot the server with a stubbed LLM are fine if marked. Tests that need the real arbiter path opt in via `@pytest.mark.real_image_gen` (see `tests/conftest.py`).

For live-stack verification (vLLM and ComfyUI both up), `tools/arbiter-smoke.py` runs 5 alternating LLM + image requests through the real call paths, asserts no OOM under a 90 s wall-clock budget, AND probes LLM output quality with a strict-JSON echo. The JSON probe is what caught the fp8-KV regression on 7B models documented in [`docs/gpu-and-models.md`](docs/gpu-and-models.md). Re-run the smoke after any vLLM version bump, model swap, or tuning-flag change.

For choosing between models (not catching drift), `bin/game model-eval run --label <name>` drives every runtime LLM surface (parser, dialogue via the real `talk` path, growth, journal, retell, examine, drift, JSON, a concurrency burst) through the production prompts and validators against whatever vLLM serves, and `bin/game model-eval compare <dirs>` writes a metrics table plus a blinded prose sheet for in-session WHIMSY grading (use a fresh subagent as the blind grader so it has never seen which model is which). Results land in `~/data/daydream/model-eval/`. The drift probes' goldens are pinned to the shipped model; a model swap re-ratifies them.

## Review & verification (batching the eyeballs)

The qualitative checks (image aesthetics, NPC voice) and the connection-overlay visual are batched and, where possible, made mechanical so a turn spends eyes-on time on gameplay, not on "does it render / read right". Three layers:

For The Village of Lost Hours the gates are different: the art gate is `bin/game prebake` plus the agent's grading in `docs/art/`, the voice gate is the model-eval canon suite plus the agent playtests (`docs/playtests/`). `bin/game review` still samples the format-1 bunny cast.

- **`bin/game review`: one offline contact sheet.** Loads `worlds/bunny.json` into a throwaway temp DB (no live server, no `live.db` touch, no API key) and writes ONE self-contained `index.html` under `~/data/daydream/reviews/<ts>/`: every aesthetic anchor render (incl. the forge), a fresh `talk` sample per authored NPC (Rook/Iris/Bram, from the shipped dialogue prompts), and a short browser-checklist for the one irreducible live glance (the connection overlay). The operator reviews everything in a single glance instead of a live reset + a browser session per check. Needs ComfyUI + vLLM up for the renders; either down degrades that section to a note. Per the GPU policy, run with the game DOWN (`daydream/review.py`).
- **Perceptual + voice regression proxies (ratify-once, then mechanical).** Image: `tests/drift/aesthetics/*.json` are dHash anchors compared to `tests/baselines/image_*.golden.json` under `tier_long`: the `forge` anchor is the authored `r-forge` seed verbatim, so a forge-render regression fails by design. Voice: `tests/test_voice_baseline.py` (`tier_short`) globs `docs/pretty/voice-samples/*.md`, classified by a `<!-- baseline-class: ... -->` marker (`tracked` / `regression-demo` / `documented-failure`), and asserts distinct narrate openers, so a new tracked baseline auto-extends the regression with no code edit.
- **Agent aesthetic review (no API key).** The aesthetic critic is THIS Claude Code agent. After `bin/game review` renders the anchors, the agent Reads each PNG and grades it against `WHIMSY.md` (cozy soft watercolor; the forge's anvil/bellows actually legible; no banned moods), recording the verdict in-session. No `litellm`, no `ANTHROPIC_API_KEY`, no runtime dependency (see the generation policy). When a human eye is genuinely wanted, escalate to `qpeek` (`bin/game test human`) or ask the operator to look in-game. (An earlier env-gated litellm vision gate was removed 2026-07-01 for needing a key; the agent does the looking instead.)
